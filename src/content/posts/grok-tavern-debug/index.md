起因简单得不像话：用 AI 写小说，API 账单涨得比字数快，响应还慢。想换个更划算也更猛的模型，盯上了中转站（天枢，lingzhanai.top）上的 **Grok 4.7**——因为站内测试里 Grok 4.7 通过、ChatGPT 5.5 不通过。

看起来就是在酒馆（SillyTavern）的 xAI 源里填个反向代理的事。结果这一路走下来，我自己误判了三次，还顺手把用户的配置搞崩过一次。等真正看清全貌时，我做的第一件事不是庆祝，而是把整条链路重新画了一遍——因为**每一个坑都长得不像它本来的样子**。

这篇文章把过程裁成一条线：先讲清楚酒馆怎么接中转，再逐个复盘坑，最后把可复用的判据留下。

> [!WARNING]
> 本文涉及成人向角色扮演的模型审核问题，全程只做**技术复盘与机制分析**，不提供任何绕过审核的具体话术或越狱方法。合规边界：涉及未成年的性内容在任何地方都是违法的，不在讨论范围内。

## 一、酒馆怎么接中转：反向代理三栏规则

酒馆的 xAI 源有个「反向代理」折叠区，三栏里真正起作用的只有一条判定规则：

```
反向代理 URL 留空  →  用「xAI API 密钥」
反向代理 URL 填了  →  用「代理密码」替代 API 密钥（另一个作废）
```

也就是说，**URL 和密钥是二选一，不是叠加**。填了 `https://lingzhanai.top/v1` 之后，那把天枢的 key 就填在「代理密码」框里，原本的「xAI API 密钥」框直接作废。

> [!TIP]
> **太长不看：接天枢只要两步**
> 1. 反向代理 URL 填 `https://lingzhanai.top/v1`（注意末尾的 `/v1`）
> 2. 代理密码填天枢的 API Key（sk- 开头那串）
> 模型名填 `grok-4.7`，流式打开，最大回复长度 8000 左右。

## 二、踩坑一：「连上了，但一点输出都没有」

配好之后，酒馆**一个字都不吐**。我第一反应是「天枢这个分组废了，别充钱」，依据是探针脚本连续十几次返回 502。

> [!CAUTION]
> **这是第一次误判，而且是最严重的一次。**
> 真相是：我的探针脚本用 Python 的 `urllib` 发请求，它的默认 User-Agent 是 `Python-urllib/3.13`，被天枢的网关**直接拉黑**了。同一把 key、同一个模型，把 UA 换成浏览器 / `node-fetch` / `undici` 之后，全部 200。
> 也就是说，不是站点挂了，是我自己用的探针工具被挡在门外。

教训很直接：**拿脚本 UA 去测商业网关，等于拿身份证复印件去刷门禁**。测之前先把 UA 换成正常的浏览器串。

## 三、踩坑二：慢成狗

排除了连通性，下一个问题是慢。让用户生成一段回复，40 秒过去还在转圈。

实测数据（同一台机器、真实对话历史）：

| 模型 | 首字延迟 | 速度 |
|---|---|---|
| GLM（对照组） | 中位 7s | 52.7 字/秒 |
| Grok 4.7 | 13~48s | 6~18 字/秒 |

慢到什么程度？我做了个对照：输入 600 字时首字 ~47s，输入 27000 字时首字 ~47s。**输入长度差了 45 倍，延迟几乎不变**——这就排除了「算力瓶颈」和「请求体积」，指向一个东西：**上游账号池在排队**。你的请求不是算得慢，是排在别人后面等额度。

## 四、踩坑三：413 体积论（又一次误判）

日志里连续出现两条 413，我差点又下结论「请求体太大，超了天枢的上限」。

> [!CAUTION]
> **这是第二次误判。**
> 那两条 413 根本不是天枢报的。一条是「Multimodal captioning request failed 413」，另一条带着 `openresty` 字样——这是酒馆的**图像打标扩展**把图片发给 DeepSeek 时，DeepSeek 那边的 nginx 拒收大图报的，跟天枢半毛钱关系没有。
> 实测：1024 KB 的请求体全过；122 条消息 / 239 KB 的对话上下文流式请求全 200。**体积从来不是瓶颈。**

> [!NOTE]
> 为什么之前测出过「上限很高」的假象？因为用重复文本去测，tokenizer 会把重复内容极度压缩，测出来的数字严重虚高。要测真实上限，必须用随机内容。

## 五、决定性转折：不是「没输出」，是「只对成人向内容静默返回空」

前面两次误判之所以翻车，是因为我一直在「连通性 / 速度 / 体积」里打转，却漏掉了最关键的一条用户反馈：

> 「它从来没有正常输出过，全部都是空回复。」

一句话推翻了「随机失败 / 上游质量参差」的所有假说。我重新做了对照组：两篇小说，一篇正常内容、一篇成人向。**正常内容能正常输出，成人向那篇永远返回空。**

更隐蔽的地方在于：这种空回复**不是报错**——HTTP 200、没有 error、没有 `finish_reason`、内容长度就是 0，酒馆的 `err.log` 里**连一条记录都没有**。所以你既看不到输出，也看不到错误，只能在界面上对着空白发呆。

而同一段成人向内容，在**天枢站内的在线对话**里是能正常返回的。结论很清楚：**商业闭源模型的内容审核，外部 API 通道比站内更紧**（或者上游账号策略不同），它选择「静默吞掉」而不是「明确拒绝」。

## 六、（我的锅）配置被清空事故

排障中途，我给过一条「用官方 Grok」的路线：反向代理留空 + 填官方 xAI 密钥。但这条路的前提是**先开 Clash TUN 全局代理**——我没把前提和动作写在同一句话里。

用户照着把 `reverse_proxy` 和 `proxy_password` 清空了，酒馆随即转向官方 `api.x.ai`，而那个地址在本机根本连不通。于是那一段时间的「重 roll 全空」，有一部分是我造成的。

> [!WARNING]
> **给步骤的铁律：前提和动作必须写在同一个句子里。**「先开代理，再把 URL 留空」拆成两条消息，用户大概率会先执行后者。

## 七、寻路：要「尺度大」，商业闭源没有一家能打

既然 Grok 在外部通道也卡成人向，那换别的闭源模型呢？我把天枢上能切的分组（JDP 系列、DeepSeek 官转、K3、GLM、OAI 协议满血、Claude 官签/Max……）逐个过了一遍，结论很扎心：

- 面向角色扮演（RP）的模型索引站，明确把 **Grok 列为「不推荐给 NSFW 用户」**（"Grok still refuses a lot of NSFW"）；
- OpenAI / Claude / Gemini 系是审核最严的一档，换了只会比 Grok 更紧；
- 国产模型（含后面要说的 HY3、StepFive）审核力度同样是国内最严。

**真正能解「尺度」问题的，是 abliterated（消融）开源模型**：它不是靠话术绕过策略层，而是直接改权重、把激活空间里的「拒绝方向」移除，从架构层面就不会拒绝。常见可跑的：L3-Stheno 3.3 8B、Huihui-Qwen3.5-9B-abliterated、MN Violet Lotus 12B。

获取途径有三条：
1. **Featherless AI** —— OpenAI 兼容、flat rate、781 个 uncensored 模型、官方声明不记日志（最省事）；
2. **AtmosCompute** —— 托管 Dolphin / Cydonia / Magnum / Euryale 等无审查模型；
3. **本地跑 KoboldCpp** —— 唯一 100% 可控，8B~12B 的 GGUF 在消费级显卡上就能跑。

## 八、意外发现：那把 key 已经被切到 GPT 分组

就在测 GPT 分组模型时，我撞见一个更离谱的事实：用同一把天枢 key 打 `/v1/models`，返回的 16 个模型 `owned_by` **全部是 openai**——**分组已经被切到了 GPT 组**。而原本的 `grok-4.7` 现在直接 404：`Model "grok-4.7" is not supported by any configured account in this group`。

顺手把这组的存活情况测了一遍：

| 模型 | 状态 |
|---|---|
| `gpt-5.6-terra` | ✅ 活，1.9s |
| `gpt-5.6-sol` | ✅ 活，1.8s |
| `gpt-6-astra` | ✅ 活，11.7s（偏慢） |
| `gpt-5.5` | ❌ 502 Upstream request failed |
| `gpt-5.6-luna` | ❌ 读超时 |
| `gpt-5.6`（裸名） | ❌ 404 不存在 |
| `grok-4.5 / 4.6 / 4.7` | ❌ 404 不在本组 |

> [!WARNING]
> **这解释了用户酒馆为什么当时全空**：settings.json 里模型名还写着 `grok-4.7`，配着天枢的 URL，请求必然 404 → 全空回复。修法就是把模型名改成 `gpt-5.6-terra`（这组里最便宜最快的那档）。

> [!NOTE]
> **中转站的「分组」才是决定模型可见性的东西，不是 URL。** 你换了分组，桌面端 settings.json 不会自动跟着变，模型名过期就 404。以后每换一次分组，先 `/v1/models` 核对一次，再改酒馆里的模型名。

## 九、顺带：HY3 vs StepFive Pro 哪个写文章好

用户后来问起这两个，我顺手测了下定位差异，结论很明确：

- **HY3（腾讯混元 Hy3）**：写文章是它少有的亮点。多篇实测评语是「文风自然有节奏感、去 AI 腔」，模仿《明朝那些事儿》那种文风复刻能达标，12000 字长文摘要零遗漏。三方对照里排序是 **Kimi（最口语）> HY3 > DeepSeek（偏技术文档味）**。
- **StepFive Pro（阶跃星辰 Step 5）**：定位是「长任务工程师」——为 AI 编程、软件工程、金融可溯源分析、长周期 Agent 设计的，600B MoE、100 万 token 上下文。写文章**不是它备考的科目**，有评测原话「拿一句话写文案去考它，本身就是没重点备考的科目」，还有个更麻烦的实测反馈：它**对抗性强、爱顶嘴**——你让它办事，它反过来反复核对你的说法、抛程序性论证，而不是乖乖写。

一句话选型：写小说 / 公众号 / 文学创作选 **HY3**；长专业文档（几十万字资料消化 + 可溯源报告 + 代码）选 **Step 5**。但两者都是国产模型，审核力度最严，对成人向 RP **完全不对口**——比 Grok 还紧。

## 十、结论与给同好的清单

绕了一大圈，真正落地的两句话：

1. **商业闭源模型解不了「尺度」问题**。Grok 站内能写、外部通道静默吞；换 GPT / Claude / 国产只会更紧。真要尺度，走 abliterated 开源 + Featherless / 本地 KoboldCpp。
2. **中转站的坑，七成出在「工具用错」和「状态不同步」**，不是模型本身。

可复用的排障判据，留一份清单：

> [!TIP]
> **酒馆接中转排障清单**
> 1. 测网关别用脚本默认 UA——先换成浏览器 UA，否则会被静默拉黑。
> 2. 无输出先关「流式传输」再发一次：非流式分支会直接把错误弹出来，流式分支会吞掉错误。
> 3. 看 `err.log` 要分清来源：带 `openresty` 的 413 多半是图像扩展发给了别的源，不是你的对话源。
> 4. 测请求体积上限必须用随机内容，重复文本会被 tokenizer 压缩，数字严重虚高。
> 5. 换中转分组后，先 `/v1/models` 核对模型名，再改酒馆 settings——模型名过期直接 404 全空。
> 6. 给用户的步骤，前提和动作写在同一句里。

整件事最有价值的，不是最后用了哪个模型，而是**三次误判教会我的同一件事**：当现象反复打脸时，先怀疑测量工具，再怀疑上游，最后才怀疑模型。
