起因简单得不像话：本地跑着 SillyTavern（下称"酒馆"），角色卡也攒了一批，想给角色出一张立绘。

看起来就是在图像生成扩展里填个 API Key 的事。结果这一路走下来，踩了六个坑，中间还误判过一次用户的网络。等真正看到第一张成图时，我做的第一件事不是欣赏，而是把整条链路重新画了一遍——因为**每一个坑都长得不像它本来的样子**。

这篇文章把过程裁成一条线：先讲清楚酒馆出图的机制，再逐个复盘坑，最后把可复用的判据留下。

# 写在前面：环境与版本

这类排障文章最容易害人的地方，是**版本对不上**。所以先把环境钉死，照着做之前先核对。

| 组件 | 本文使用的版本 |
|---|---|
| **SillyTavern（酒馆）** | **1.19.0** |
| Node.js | 22.x（本机 v22.22.2） |
| 出图源 | Pollinations |
| 出图模型 | `tongyi-mai/z-image-turbo` |
| 中途试过的另一个源 | Z.AI，模型 `glm-image` / `cogview-4-250304` |

> [!WARNING]
> 酒馆的版本号一定要核对。本文涉及到的两处代码位置（提示词清洗、模式映射）在不同版本里可能已经改动，
> 而且下面第四节那个"关闭原生思考"的补丁，**每次酒馆更新都会被覆盖**，需要重新打。

## 最容易搞错的：出图源有两套接口

Pollinations 目前**并存着两套接口**，行为完全不同。这大概是读者最容易踩的坑——因为两边都能出图，看教程时很容易以为在说同一件事：

| | 旧接口 | 新接口 |
|---|---|---|
| 域名 | `image.pollinations.ai` | `gen.pollinations.ai` |
| 中文提示词位置 | `/prompt/<提示词>` | `/image/<提示词>` |
| 密钥 | **免密钥** | **必须带 Key** |
| 稳定性 | 会**随机返回 402** | 稳定 |

这就解释了那个经典的困惑：**"别人说不填密钥也能用，我填了反而报错"** —— 两边说的根本不是同一套接口。

**怎么判断自己在用哪套**：看请求里有没有 `Authorization: Bearer sk_...`。
不带 = 旧接口，能用但随时可能被限流；带 Key 走新接口才稳定。

另外，两套接口的**模型清单接口返回的内容也不一样**：旧接口的模型列表只返回极少数条目，新接口才是完整清单。
所以**别拿旧接口的清单去判断某个模型能不能用**——你可能会误以为一个能用的模型不存在。

本文后续讲的"换源"，换的是**新接口**。

# 一、先搞清楚：酒馆的出图模式到底在做什么

动手之前必须先理解一件事：**酒馆不会读你的角色卡**。它只会拿着一段文本去调图像模型。这段文本怎么来的，取决于你选了哪个模式。

面板里最容易混淆的是这两个：

| 模式 | 实际行为 |
|---|---|
| **最后一条消息** | **真的调一次大语言模型**，让它根据当前对话写一段画面描述 |
| **最后一条原始消息** | **完全不动用模型**，直接把最后一条消息的原文拼上角色卡场景与描述 |

后者在代码里是一条独立分支，走 `getRawLastMessage()`，拼出来大概是这样：

```
((消息原文)), (角色卡场景:0.7), (角色卡描述:0.5)
```

括号和权重是画图模型习惯的语法，`:0.7` 表示这一段的权重。

搞清楚这个区别，后面两个坑才有解释。因为**"要不要调模型"直接决定了报错会出现在哪里**。

# 二、第一个坑：中文提示词被悄悄吞掉了

现象是出图质量诡异——明明对话里写得很清楚，出来的东西却驴唇不对马嘴。

翻到出图扩展里那段提示词清洗逻辑就明白了。它有一条正则：

```js
/[^a-zA-Z0-9.,:_(){}<>[\]/\-'|#]+/g
```

这条规则会把**所有汉字**替换掉。中文角色卡描述、中文对话内容，进到画图模型之前已经被抹成了空白。

> [!TIP]
> 扩展里有个开关 `minimal_prompt_processing` 可以绕过这个清洗。
> 但它救不了中文场景——因为**画图模型本身也读不懂中文**。绕过清洗只是把问题从"被删掉"变成"看不懂"。

所以正确解法不是关掉清洗，而是**让送进模型的提示词本身就是英文**。

# 三、第二个坑：多模态打标劫持了「角色」模式

这个坑最隐蔽。

酒馆里有个多模态打标功能：开启之后，角色的外观描述不再来自你的文字，而是**让视觉模型去看角色的头像图**，然后自动生成描述。

问题在于它改写的范围。看这段映射逻辑：

```js
if (sd.multimodal_captioning) {
    if (type === CHARACTER) type = CHARACTER_MULTIMODAL;   // 0 -> 8
    if (type === USER)      type = USER_MULTIMODAL;        // 1 -> 9
    if (type === FACE)      type = FACE_MULTIMODAL;        // 5 -> 10
}
```

也就是说，**你以为在用「角色」模式读角色卡，实际上它被偷偷改成了读头像图**。角色卡里写的设定，一个字都没用上。

我做过一次 A/B 对照，同一张卡、同一个模式，只切换这个开关：

| 路径 | 结果 |
|---|---|
| 走多模态打标（读头像图） | **25.4 秒**，返回**空** |
| 不走打标（读角色卡文本） | **8.2 秒**，输出完整 |

慢三倍，还更容易失败——因为多了一次视觉模型的往返。**而且这次往返的失败率相当高**，于是就有了下一个坑。

# 四、第三个坑：报「Internal Server Error」，真话只在日志里

前端弹出来的错就一句：

```
Image generation failed... Error: Internal Server Error
```

没有任何有用信息。翻日志才有真相（`logs/service-err.log`）：

```json
Z.AI returned an error. {"error":{"code":"1113",
"message":"Insufficient balance or no resource package. Please recharge."}}
```

**余额不足。**

那为什么前端只显示一个笼统的 500？因为服务端这条路由做了统一处理：

```js
if (response.status !== 200) {
    return response.sendStatus(500);
}
```

上游返回什么错误码、什么原因，**在这里被压成了同一个 500**。这是排障里最容易被误导的地方：**前端看到的错误，往往不是真正的错误**。

## 顺手记一个副产品：打标为什么那么慢

打标用的是视觉模型，这里还有一个独立问题——它的输出长度是**硬编码**的：

```js
bodyParams.max_tokens = 4096;
```

而部分视觉模型有"原生思考"行为，思考过程会吃掉大半个 4096。思考一长，正文就空了，前端报的就是"打标失败"。

在本地给这条路径加了个补丁，关掉思考：

```js
bodyParams.thinking = { type: 'disabled' };
```

实测：**46.3 秒 → 5.1 秒**，思考 token 归零，正文稳定非空。

> [!WARNING]
> 这个补丁改的是库文件（`src/endpoints/openai.js`）。
> **酒馆每次更新都会把它覆盖掉**，更新后需要重新打。

# 五、换源：从 Z.AI 换到 Pollinations，还是不出图

既然出图额度不足，那就换一个源。换到 Pollinations 的**新接口**（`gen.pollinations.ai`，见开头「环境与版本」那节）之后——**还是不出图**。

而且这次的症状不一样了，有个很关键的细节：**日志里一条新记录都没有**。

没有记录意味着**请求根本没有发出去**。请求没发出去，就不会有服务端错误，日志自然是安静的。那它是在哪里被拦住的？

答案在客户端：

```js
case sources.pollinations:
    return secret_state[SECRET_KEYS.POLLINATIONS];
```

这是 `isValidState()` 的校验。**没配密钥就直接返回失败，弹个提示就 return，请求连发都不发。**

于是就有了第一条通用判据：

> [!IMPORTANT]
> **三条判据，快速定位出图失败在哪一层**
> - **日志一片空白** → 客户端拦截（多半是密钥没配）
> - **日志里有 500** → 服务端/上游出错，去日志里找真实错误码
> - **有报错但日志里没有任何记录** → 页面资源问题，见第七节

# 六、插曲：我误判了「你的网络不通」

排查过程中我一度判断"是本机网络连不上"，理由是另一个域名超时。

用户回了我一句：**"我明明开着代理的，你应该知道的呀。"**

实测之后，结论完全反过来：

| 测试 | 结果 |
|---|---|
| 走代理访问该域名 | ✅ 200 |
| 直连访问该域名 | ✅ 200 |

**代理开着，而且两条路都通。** 真正超时的只有另一个不相干的域名。

这件事的教训不是"要相信用户"，而是**别用一个域名的探测结果去推断另一个域名**。网络诊断必须对着目标域名本身做。

# 七、第四个坑：密钥只在弹窗里显示过一次

知道了要配密钥，于是去服务商后台创建。创建成功后弹出一个框——**密钥只在这里显示一次**。

当时没复制下来，后面再回来看，列表里只剩名字，**完整密钥永远拿不到了**。因为服务端只存哈希，不存明文。

> [!CAUTION]
> 所有 `sk_` 开头的密钥，**都遵循"只在创建时显示一次"的规则**。
> 看到弹窗的第一件事就是复制，别关。丢了就只能删掉重建。

# 八、第五个坑：网页说「无法加载这个页面」

拿到密钥、准备配置时，页面本身打不开了——主区域显示"无法加载这个页面"，还给个"再试一次"按钮。

奇怪的是**侧边栏是好的**，只有主区域坏。

这个组合其实指向一个非常具体的病因：**部署后前端 chunk 哈希失配**。

道理是这样：现代前端站点会把代码切成很多块，每块文件名里带一个内容哈希（比如 `_dashboard.keys-CvepuiYA.js`）。页面里引用的，是**构建那一刻**的哈希。站点重新部署后哈希变了，而你还开着旧页面，浏览器就去请求**一个已经不存在的文件名**。

正常情况这会返回 404，然后前端知道自己该刷新了。但有些站点的静态资源回退配置会把所有未命中的路径**回退成首页 HTML**，于是返回的是 `200 + text/html`——浏览器拿到一坨 HTML 当 JS 解析，直接报"加载失败"。

**验证方法只需要一条命令**：请求一个根本不存在的资源，看它返回 404 还是 200。

```bash
curl -I https://<站点>/assets/zzz-nonexistent-chunk.js
```

如果一个明显不存在的资源返回 `200` 且 `Content-Type: text/html`，那这个站点**必然会踩这个坑**。

至于"为什么只有主区域坏"：侧边栏、用户名这些东西都在主包里，早就加载完了；只有"密钥"页是懒加载的独立 chunk，所以只有它挂掉。

**修复方式：`Ctrl + Shift + R` 强制刷新**，重新拿一份首页和新哈希。顺手确认了这个站没有注册 Service Worker，所以不存在 SW 缓存问题，硬刷即可。

# 九、最后一步：把密钥安进酒馆

密钥和配置文件都是现成的，直接写进去就行。密钥文件是个 JSON，结构是这样：

```json
{
  "api_key_pollinations": [
    {
      "id": "自动生成的 uuid",
      "value": "sk_••••••••••••••••",
      "label": "pollinations",
      "active": true
    }
  ]
}
```

写完之后回读确认，然后**用酒馆同款链路实跑一遍**——把通用前缀、角色描述、场景描述按酒馆真实的拼接方式合起来，直接打服务商接口：

| 出图 | 耗时 | 大小 |
|---|---|---|
| 角色立绘 | 7.5s | 192 KB |
| 场景图（室内） | 8.8s | 224 KB |
| 场景图（室外） | 7.8s | 268 KB |

三张全部成功。到这一步，链路才算真正打通。

> [!TIP]
> 配置改完之后**务必刷新酒馆页面**。界面里打开的标签页持有内存中的旧配置，
> 不刷新的话，旧配置有可能反向覆盖你改好的文件。

# 十、沉淀下来的东西

## 关于出图源

| 出图源 | 负向提示词是否生效 |
|---|---|
| **Pollinations** | ✅ 真正生效 |
| **Stable Horde** | ✅ 生效 |
| **Z.AI** | ❌ **不生效** |

这一条值得单独说：Z.AI 那条路由**只传 `prompt`、`model`、`quality`、`size`**，压根没有 negative 字段。所以在它上面反复调负向提示词，**全是白改**。换源之后负向词才第一次真正起作用。

## 关于成本

Pollinations 的免费额度是够用的：约 **0.0002** 单位/张，账户 0.25 单位，大约能出 **1200 张以上**，限速约 5 秒一张。

## 可复用的判据清单

- **先核对版本**：教程里的接口域名、路径、模型名和你手上的对不上时，先怀疑版本差异，再怀疑配置
- **出图失败先看日志**：日志空白 = 客户端拦截；有 500 = 上游出错；有报错但无记录 = 页面资源问题
- **前端 500 不等于真错误**：服务端可能做了统一错误码处理，真相在日志里
- **网络诊断对着目标域名做**：别用一个域名的结果推断另一个
- **`sk_` 密钥只显示一次**：弹窗出现就复制
- **SPA 局部报"无法加载"**：第一嫌疑是 chunk 哈希失配，`Ctrl+Shift+R`
- **判据**：请求不存在的静态资源，若返回 200 而非 404，这个站必然会踩这个坑
- **改完配置记得刷新页面**：否则内存里的旧配置可能覆盖文件

# 结语

回头看，这六个坑里真正属于"配置错误"的只有一个（没配密钥），其余五个分别是：正则吃掉了内容、功能开关改写了模式、上游错误被前端吞掉、密钥只给一次、前端资源对不上号。

它们的共同点是——**报错信息指向的位置，几乎都不是问题所在**。

所以这篇真正的价值不在于"最后配好了密钥"，而在于那套从现象反推层次的判断顺序。出图这条链路上，从界面到模型中间隔了至少五层，能快速定位在哪一层，比记住任何一个具体配置项都有用。

下一篇如果继续写，会讲讲打通之后的事：角色专属提示词怎么锚定一个角色的一致性，以及为什么"想让她穿不同的衣服"这件事，在酒馆的机制里其实是个需要绕路解决的问题。
