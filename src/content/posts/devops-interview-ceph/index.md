面试官问：「Ceph 的 MON 为什么要部署三个？」

我说：「为了提高高可用。」

他接着问：「那为什么剩两个可以，剩一个就不行？」

我卡住了。

那三秒钟里我脑子里转的是「一个人也能开会啊，一个人拍板不是更快吗」。这个直觉听起来甚至挺有道理，但它是错的，而且错得很典型：把分布式系统的共识，当成了普通开会。

这篇就从这道题开始，把 Ceph 和灾备这两块最容易「背了但说不清」的东西过一遍。

> [!TIP]
> 灾备运维岗位不需要把 Ceph 学到源码级。但下面这些必须能讲清楚，按优先级排：
>
> **第一优先**：Ceph 架构、MON/MGR/OSD、副本、CRUSH、OSD 故障、数据恢复、扩容
> **第二优先**：Ceph 与 Kubernetes、CSI、PV/PVC、持久化存储
> **第三优先**：灾备、备份、恢复、RPO/RTO、恢复演练
> **第四优先**：商业备份软件的基本概念和工作流程

## 一、Ceph 存储

### 1.1 先说清楚它是什么

用一句自己的话：

> 「Ceph 是一个分布式存储系统，能提供对象存储、块存储和文件存储。它由多节点组成存储集群，把数据分布到不同节点上，从而提高可靠性、扩展能力和容错能力。」

核心组件，这个必须会：

| 组件 | 职责 |
|---|---|
| **MON**（Monitor） | 维护集群状态、集群地图（Cluster Map） |
| **OSD** | 真正负责数据存储、复制、恢复 |
| **MGR** | 集群管理、监控、管理接口 |
| **MDS** | CephFS 使用，负责文件系统元数据 |
| **RGW** | 提供对象存储接口 |

> [!WARNING]
> 别为了显得厉害，把没实际管过的组件说成「熟练」。
>
> 可以这么讲：「我主要接触 MON、MGR、OSD，项目里重点是 OSD 和整个存储集群的运维管理。」
>
> 说得少但接得住追问，比说得多然后被问穿强十倍。

**「你们为什么用 Ceph？」** 结合项目答：

> 「项目里主要是给 Kubernetes 提供持久化存储，同时需要跟随业务增长做存储集群的扩容和管理。」

### 1.2 OSD 是什么，为什么会坏

一句话：**OSD 是集群里真正存数据的工作单元**，一般对应一块或多块物理盘。

OSD down 了的答法：

> 「先通过 Ceph 状态确认是哪个 OSD 异常，然后检查对应服务器和磁盘状态，再结合日志判断是磁盘故障、网络问题还是 OSD 服务本身的问题。确认是硬件故障之后，根据业务情况做替换和恢复，同时观察集群恢复状态，最后确认数据和集群状态都恢复正常。」

常用命令：

```bash
ceph -s                  # 集群状态（注意是 ceph -s，不是 safe-S）
ceph health              # 健康状态
ceph health detail       # 详细健康信息
ceph osd tree            # 看 OSD 的层级、节点以及状态（很实用）
ceph osd status          # OSD 状态
```

> [!CAUTION]
> `systemctl status ceph-osd@3` 这个命令不是所有环境都能直接用，取决于安装方式和服务管理方式。面试时别把它说死。
>
> 更稳的说法：*「我会先确认 osd.3 在哪个节点，然后在对应 Linux 节点上检查 OSD 进程或服务状态。如果是 systemd 管理的，就用 systemctl 看对应的 Ceph OSD 服务，同时结合 Ceph 日志判断具体原因。」*
>
> 知道「为什么执行这个命令」，比背住命令重要。

### 1.3 OSD 之间怎么通信

先纠正一个常见误解：OSD 之间不是靠某个类似 Nginx 的独立「通信服务」。**它们主要通过网络直接通信**，底层用 Ceph 自己的通信机制。

> 「Ceph 的 OSD 之间主要通过网络通信。OSD 会和 MON、MGR 以及其他 OSD 通信，用于集群状态同步、数据读写、数据恢复和心跳检测。网络层面用 TCP/IP，具体端口随 Ceph 版本和配置不同，实际排查时我会结合配置和监听端口确认。」

三类关系：

| 关系 | 用途 |
|---|---|
| **OSD ↔ OSD** | 数据复制、恢复、重新均衡、心跳与状态判断 |
| **OSD ↔ MON** | 集群状态与集群地图同步 |
| **OSD ↔ MGR** | 集群管理、监控、管理接口 |

> [!IMPORTANT]
> **端口号千万别死背。** 不同版本默认端口范围和配置都可能不一样。
>
> 标准说法：*「Ceph 不同版本的端口配置有区别。实际排查时我会用 `ss -lntp`、`netstat` 看当前监听情况，再结合防火墙和网络连通性一起判断。」*

### 1.4 一台机器跑多个 OSD，怎么通信

```
Server A
├── OSD.1
├── OSD.2
└── OSD.3
```

`OSD.1`、`OSD.2`、`OSD.3` 本质上是三个独立运行的进程。

同一台机器上的 OSD，通信走本机网络协议栈，不需要真的出网卡去绕交换机：

```
OSD.1 → Linux TCP/IP 协议栈 → OSD.2
```

跨机器的就必须走物理网络：

```
OSD.1 → TCP/IP → 网卡 → 交换机 → 网卡 → TCP/IP → OSD.4
```

> 「一台服务器可以跑多个 OSD，每个 OSD 都是独立服务。OSD 之间通过 Ceph 的网络通信机制交互，本质还是 TCP/IP。同节点的通信主要经过本机协议栈，不需要外部交换机；跨节点就要经过网卡、交换机和协议栈。所以排查通信问题时，我会先看节点之间的 IP 连通性，再看 TCP 连接、OSD 状态和日志。」

> [!CAUTION]
> 别说「一个服务器就是一个 Ceph 集群」。
>
> 准确说法：**一个 Ceph 集群可以由多个节点组成，一台服务器上也可以跑多个 OSD。**

「能不能 ping 两个 OSD」这题，答案是：可以排查，但别理解成给 OSD 做 ping。ping 验的是 IP 层，OSD 是应用进程，真正的通信还涉及 TCP 连接和 Ceph 自身的状态。

### 1.5 排查的层次感（这段最实用）

记住这个顺序，面试时沿着往下讲就不会乱：

```
Ceph 状态 → OSD 进程 → 网络连通性 → TCP连接/端口 → 日志 → 磁盘/IO
```

```bash
ceph -s / ceph health detail     # ① 集群状态：有没有 OSD down、网络告警
ps -ef | grep ceph-osd           # ② 进程是否存在
ss -antp | grep ceph-osd         # ③ TCP 连接状态
ping 192.168.1.101               # ④ IP 层连通（只能证明 IP 可达）
nc -zv 192.168.1.101 <端口>      # ④ 端口连通
# ⑤ OSD 日志
# ⑥ 磁盘 I/O
```

看 `ss -antp` 时留意有没有大量 `ESTAB`、`TIME-WAIT`、`SYN-SENT`、`SYN-RECV`。

> 「我会先用 `ceph -s` 和 `ceph health detail` 确认有没有 OSD down 和网络告警，然后检查节点之间的网络连通性、Ceph 相关端口是否监听、防火墙策略，之后结合 OSD 日志判断是网络、进程还是底层磁盘的问题。」

日志里如果大量 heartbeat 超时或连接异常，说明 OSD 进程还活着，但它和其他节点之间的通信已经不正常了。

### 1.6 MON 为什么至少三个（回到开头那道题）

MON 的职责：维护集群状态和集群地图。

**为什么要多个**：为了提高管理面的高可用和容错。只有一个 MON 时，它一挂，整个集群就做不了状态变更。

但面试官真正想听的是下一层：为什么剩两个行，剩一个不行？

多数人的直觉是：「两个人表决容易僵住，一个人反而好办事。」

**错就错在这里。** MON 不是开会成员，它需要确认自己看到的集群状态，是不是整个集群认可的状态。

只剩一个 MON 时，它不知道另外两个为什么消失。可能是真挂了，也可能只是自己跟它们网络断了。这就是网络分区。

如果它在没有多数派的情况下自己认定「我就是整个集群的正确状态」，就会出现脑裂，或者集群状态不一致。

所以 Ceph 的选择是：**宁可在没有 quorum 的时候限制部分状态变更，也不让一个孤立的 MON 自己拍板。**

> [!TIP]
> 一句话记住：**能不能自己运行，和能不能代表整个集群形成共识，是两件事。**

> 「MON 需要通过 quorum 保证集群状态一致。3 个挂 1 个，剩下 2 个还能形成多数派；只剩 1 个就无法形成 quorum，所以 Ceph 不会让这个孤立的 MON 单独代表集群做状态决策。」

这个深度就够了。**不用往 Paxos / Raft 选举算法里钻**。被追问到算法层，如实说「选举算法细节我没深入」比硬编好得多。

### 1.7 数据怎么分布到 OSD（CRUSH 与 PG）

先破一个错：**MGR 不负责数据放哪。** 它管的是管理接口和监控，不参与数据放置决策。

正确的映射链：

```
客户端 → Pool → PG → CRUSH → OSD
```

一层层看：

```
一份数据
   ↓
Pool
   ↓
PG（Placement Group，数据映射和管理的中间层）
   ↓
CRUSH 算法（按集群拓扑、故障域、副本策略计算）
   ↓
选出合适的 OSD
   ↓
OSD 存数据
```

> 「主要靠 PG 和 CRUSH。数据先映射到对应的 PG，CRUSH 再根据集群拓扑、故障域和副本策略算出该用哪些 OSD，最终把数据分布过去。这样能尽量让副本落在不同故障域，提高可靠性。」

三副本的意思：

> 「同一份数据存三份，尽量分布在不同故障域。单个 OSD 或节点故障时，其他副本仍然能提供数据。」

### 1.8 副本不等于备份

> [!IMPORTANT]
> 这是整篇最该记住的一条：**Ceph 的副本机制恢复不了误删的数据。**

业务层把数据删了，这个删除操作通常也会同步到其他副本。副本挡不住误删。

| 机制 | 主要解决什么 |
|---|---|
| **Ceph 副本** | 磁盘、OSD、节点故障，提高可用性 |
| **备份** | 误删、误操作、数据损坏、勒索 |
| **快照** | 保存某个时间点的状态，特定场景下可恢复 |

> 「业务方误删一批数据，Ceph 的副本本身恢复不了。副本是为了提高可用性和容错，比如某个 OSD 或节点挂了，其他副本还能保证访问。但业务层删除数据时，这个删除通常也会同步到其他副本，所以副本不能替代备份。真要恢复误删，还是得靠独立的备份、快照或者其他恢复机制。」

### 1.9 Ceph 和灾备不是一回事（主动说出来会加分）

> **Ceph 解决的是「数据怎么可靠地存」；灾备解决的是「大范围故障之后，业务和数据怎么恢复」。**

| | Ceph 副本 | 灾备 |
|---|---|---|
| 场景 | 一块 OSD 挂了 | 整个存储集群、机房、区域故障 |
| 解决 | 其他副本还能提供数据，Ceph 自动恢复 | 有没有另一套副本，能不能恢复业务 |
| 指标 | 无 | **RTO / RPO** |

面试里主动讲这个区别，说明你理解的是体系，不只是一个存储软件。

### 1.10 Ceph 配 Kubernetes

简历里 K8S 和 Ceph 都写了，这题几乎必问。

**「Kubernetes 为什么要用 Ceph？」**

> 「Kubernetes 里容器是动态的，容器删了本地数据可能就没了。所以数据库、业务文件这类需要持久化的数据，得用持久化存储。Ceph 能提供可靠的分布式存储，通过 CSI 给 Kubernetes 提供持久化卷。」

**「Ceph 扩容怎么做的？」** 简历写了就一定会被问：

> 「之前负责过 Ceph 集群的扩容和变更。扩容时先确认现有集群状态和容量，检查节点和磁盘资源，然后加入新的存储资源，观察数据重新分布和集群恢复情况，最后确认集群状态和业务访问正常。」

**追问「扩容之后为什么要观察」**：

> 「新增 OSD 会触发数据重新均衡，也就是迁移。如果集群负载高，就得关注恢复和迁移对业务 I/O 的影响，同时确认集群最终回到正常状态。」

## 二、灾备与数据恢复

### 2.1 「你做过灾备吗」

这是灾备岗的开场必问题，也最容易一句话答死。

> [!CAUTION]
> 绝对不要说「我没做过灾备」。这句话一出口，后面所有问题都会变成「那你为什么来投这个岗位」。

正确答法的核心是**重新定义边界，不是否认**：

> 「我之前主要做云平台和运维，项目里参与过数据灾备和恢复方案。比如在 Ceph 环境里，负责数据完整性校验、恢复计划制定和故障恢复验证。虽然没有长期使用专门的商业备份软件，但对灾备体系、备份流程、恢复演练有实践经验，也具备快速学习能力。」

追问「你了解灾备吗」，按五层展开：

> 我理解灾备主要是保障业务连续性，包括：
> 第一，数据备份；第二，数据恢复；第三，恢复演练；第四，容灾切换；第五，RTO 和 RPO 管理。

**RTO 和 RPO 这两个词一定得说出来。** 它们是这个领域的行话，说出来对方就知道你懂。

### 2.2 手里有一份备份，怎么恢复

面试官问法：业务方误删数据，你手上有一份之前的备份，准备怎么恢复？你会先做什么，而不是直接把备份覆盖回去？

> [!CAUTION]
> **不要直接覆盖。** 这是这题唯一的死穴。

原则：先用备份恢复出一份数据做验证，确认无误再执行正式恢复。

> 「我不会直接用备份覆盖现有数据。我会先用备份恢复出一份副本做验证，确认数据完整性和时间点是否符合预期，同时确认恢复操作不会影响现有业务数据。验证通过之后，再按恢复计划执行正式恢复，恢复完成再做完整性校验和业务验证。」

### 2.3 备份本身坏了怎么办

> [!IMPORTANT]
> 核心原则：**不继续强行恢复。**

> 「发现备份损坏，我不会继续强行恢复，而是先确认损坏范围，再检查其他备份、历史备份或者其他副本，评估可用的恢复点。同时把情况同步给业务方和负责人，说明当前能恢复到哪个时间点、可能丢多少数据。」

这题不用讲深，抓住四件事就够：不强行恢复、先确认范围、找替代恢复点、及时同步。

### 2.4 备份失败怎么排查

标准六步：

> 1. 查看备份任务日志
> 2. 检查网络连接
> 3. 检查存储空间
> 4. 检查权限和账号
> 5. 检查源端服务状态
> 6. 验证恢复是否正常

重点在第 6 步。**备份成功的唯一验证标准是「能恢复」**，不是「任务返回成功」。任务成功但恢复不出来，这种事发生得比你想象的多。

### 2.5 为什么想转灾备

> 「我原来的工作涉及云平台、存储、容器和数据恢复。灾备更聚焦数据安全和业务连续性，我认为这是未来很重要的方向，也希望在已有的运维基础上往深了走。」

## 附录：一页纸速查

**Linux 排障**

```bash
top / free -h / vmstat 1          # CPU、内存、整体负载
iostat -x 1 / iotop / pidstat -d 1 # 磁盘 IO 与进程 IO
df -h / df -i                     # 空间与 inode
ss -lntp / ss -antp               # 端口监听与连接
nc -zv IP PORT                    # 端口连通性
journalctl -u 服务名 --since       # 服务日志
crontab -l / last / dmesg | grep oom  # 定时、重启、OOM
show processlist / show engine innodb status  # MySQL
explain select ...                # 执行计划
```

**Kubernetes 排障**

```bash
kubectl get pods / describe pod <pod>     # 状态与 Events（Pending 第一步）
kubectl logs <pod>                        # 应用日志
kubectl get svc / endpoints <svc>         # Service 与后端映射
kubectl top nodes / describe node <node>  # 节点资源
kubectl rollout history / undo            # 版本与回滚
```

**Ceph 排障**

```bash
ceph -s / ceph health detail              # 集群状态
ceph osd tree / ceph osd status           # OSD 层级与状态
ps -ef | grep ceph-osd                    # 进程
ss -antp | grep ceph-osd                  # TCP 连接
ss -lntp                                  # 确认实际监听端口（不要背固定端口）
```

**三个必背的「不等于」**

1. **Java 进程存在 ≠ 应用正常提供服务**（还要看端口和绑定地址）
2. **ping 通 ≠ 业务通**（ICMP 可达 ≠ 端口可达）
3. **Ceph 副本 ≠ 数据备份**（副本防硬件故障，备份防误删）

**两个必背的设计思想**

1. **声明式管理**：改 Deployment，不改 Pod。改的是期望状态
2. **Taint 在 Node、Toleration 在 Pod**：控制权在资源侧

## 写在最后

这份宝典里的题目，都来自同一个人被连续追问几十轮的真实过程。里面那些「错误回答」不是编出来凑数的，是真发生过的，包括把 `crontab` 说成 current type、把 OSD 说成 OST、把 Ceph 说成 safe。

技术部分可以靠刷题补。「被追问到第三层还答得上来」这件事，只能靠真实经历。

所以最实在的建议是：把每一题都换成你自己项目里真实发生过的场景，然后对着讲三遍。讲到第三遍，你就不需要背了。
